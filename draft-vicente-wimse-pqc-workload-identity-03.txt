                PQC Agility for WIMSE Workload Identity
              draft-vicente-wimse-pqc-workload-identity-03

Abstract

   This document defines PQC algorithm agility requirements and
   migration mechanisms for the WIMSE (Workload Identity in Multi System
   Environments) framework.  It specifies how workload identity tokens,
   SVID certificates, and trust bundles transition from classical to ML-
   DSA and hybrid composite algorithms, with epoch-aware rotation
   coordinated by the Sanctum rotation orchestration framework.

   This revision (-03) adds normative requirements for hybrid SVID
   certificates, epoch-signaling in SPIFFE trust bundles, and alignment
   with draft-vicente-pquip-pqc-rotation-orchestration.

1.  Introduction

   Workload identity systems (SPIFFE, SPIRE, and WIMSE-compliant
   implementations) issue short-lived X.509 SVIDs and JWT-SVIDs to
   authenticate workloads in cloud-native environments.  As these
   environments migrate to PQC, every issued credential must carry a PQC
   or hybrid composite signature, and trust bundles must reflect current
   PQC signing key epochs.  This document defines the algorithm agility
   profile and orchestration requirements for PQC migration in WIMSE
   deployments.

2.  Terminology

   BCP 14 [RFC2119] [RFC8174] applies.

   SVID:
      SPIFFE Verifiable Identity Document.  An X.509 certificate or JWT
      carrying a SPIFFE ID as a Subject Alternative Name.

   Trust Bundle:
      The set of CA certificates and signing keys trusted by a SPIFFE
      trust domain.

   PQC-SVID:
      An SVID signed with an ML-DSA or hybrid composite key as defined
      in this document.

3.  PQC-SVID Requirements

   WIMSE deployments conformant with this profile MUST issue X.509 SVIDs
   signed with ML-DSA-65 or ML-DSA-87.  Hybrid composite SVIDs (ML-DSA +
   ECDSA P-256) SHOULD be issued during the transition period for
   backward compatibility with relying parties that cannot yet validate
   ML-DSA signatures.  The PQCHC extension (draft-vicente-lamps-pqchc)
   MUST be included in PQC-SVIDs to bind the ML-DSA and classical key
   components.

   JWT-SVIDs in PQC-capable WIMSE deployments MUST use the ML-DSA
   algorithm identifier in the JOSE header.  The epoch_id MUST be
   included as a private claim (pqc_epoch_id) in the JWT payload.

4.  Trust Bundle Epoch Signaling

   SPIFFE trust bundles extended for PQC deployments MUST include an
   epoch_id field at the trust domain level.  The trust bundle refresh
   endpoint MUST return the current epoch_id and MUST include both the
   current and previous epoch's signing certificates during the grace
   period following epoch rotation.  Trust bundle consumers MUST reject
   bundles where the included epoch_id is lower than the highest
   previously accepted epoch_id for that trust domain.

5.  Integration with Rotation Orchestration

   WIMSE Signing Authorities participating in orchestrated PQC rotation
   (draft-vicente-pquip-pqc-rotation-orchestration) MUST register as
   protocol stacks with the Rotation Orchestrator.  The Signing
   Authority MUST emit an epoch readiness signal when its trust bundle
   has been updated with the new epoch's certificate and all in-flight
   SVID issuance operations have completed.  SVID issuance MUST be

6.  Security Considerations

   PQC-SVIDs provide HNDL resistance for workload-to-workload
   authentication.  The epoch_id claim in JWT-SVIDs prevents replay of
   credentials issued under a compromised prior epoch.  Trust bundle
   consumers MUST implement the epoch monotonicity check to prevent
   epoch-rollback attacks.  WIMSE Signing Authorities MUST use HSM-
   backed ML-DSA signing keys where deployment environment permits.

7.  IANA Considerations

   IANA is requested to register the pqc_epoch_id JWT claim name in the
   IANA JSON Web Token Claims registry.
